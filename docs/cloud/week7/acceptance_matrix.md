## Additional observed recovery

The first successful Week 5 retry committed seq 21–23, then dbt failed because the initial non-incremental CTE had `WHERE FALSE` without a `FROM`. The lock was released, checkpoint 23 remained committed, and pointer 0 remained unpublished. After a one-line BigQuery SQL correction and r3 image deployment, the exact same manifest returned `Week 5 NO_OP`, passed dbt tests/reconciliation, and published pointer version 1. See [`dbt_failure_and_recovery.json`](dbt_failure_and_recovery.json).

The r4 currentness fence was separately verified: after a controlled candidate failure the pointer remained not-current and the public view returned zero rows; after the exact-manifest recovery, the same pointer version was current again and the public view returned all five rows. A one-time `403` in the post-publication Workflow status query was fixed with read-only IAM on the singleton pointer table and confirmed by a `NO_OP` replay.

All ten failure drills have live receipts. The pointer currentness fence was added after the first controlled batch tests; ORC-07 and ORC-10 verify that the public view becomes empty after Silver commits and is restored only by a successful publication.
